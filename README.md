# 建模大赛GitHub协作仓库 README

## 一、仓库简介

本仓库为**建模大赛专属协作仓库**，用于统一存放建模论文、代码、数据集、模型文件、分析报告等所有赛事资料。为保障团队多人协作高效、版本统一、文件不冲突，特制定本协作规范，所有团队成员必须严格遵守，适用于本次首次建模大赛GitHub协同开发。

仓库核心目标：文件分类清晰、版本可追溯、修改可溯源、全程无冲突、成果完整可直接提交赛事系统。

## 二、Git \& GitHub 基础协作用法（新手适配）

### 2\.1 基础环境准备

1\. 所有成员本地安装Git工具，配置用户名和邮箱（与GitHub账号一致）；

2\. 注册并登录GitHub账号，加入本团队仓库协作权限；

3\. 本地克隆仓库，仅首次操作执行：`git clone 仓库地址`，将远程仓库文件同步到本地。

### 2\.2 核心常用命令（团队协作必备）

**1\. 拉取远程最新代码（每日操作第一步）**

每次开始修改文件前，必须先拉取远程最新内容，避免版本冲突：`git pull`

**2\. 查看文件修改状态**

查看本地哪些文件被修改、新增、删除：`git status`

**3\. 暂存修改的文件**

将修改后的文件加入暂存区，准备提交：`git add .`（全部文件）/ `git add 文件名`（单个文件）

**4\. 本地提交修改（必须写清晰备注）**

保存本地修改记录，备注需包含修改人、修改内容：`git commit -m "张三：更新建模数据预处理代码，修正异常值"`

**5\. 推送本地内容到远程仓库**

将本地修改同步到GitHub远程仓库：`git push`

### 2\.3 分支协作规范（新手简易版）

为避免多人直接修改主分支造成冲突，本次大赛统一采用**分支开发、主分支保护**模式：

1\. **main主分支**：仅存放最终定稿、无错误、可提交的完整成果，禁止直接修改、强制推送；

2\. **个人分支**：每位成员新建个人专属分支（命名：姓名/职责，如zhangsan/code、lisi/paper），所有修改均在个人分支完成；

3\. 个人修改完成后，提交Pull Request（PR），由团队负责人审核后合并到主分支；

4\. 合并完成后，所有成员及时拉取主分支最新内容，保持本地版本同步。

## 三、文件版本管理规范

### 3\.1 文件目录与命名规则

为保证仓库整洁、版本可追溯，统一文件存放目录和命名格式，禁止随意新建文件夹、乱命名文件。

**统一目录结构**：

- **/code**：所有建模代码、脚本、程序文件

- **/data**：原始数据集、清洗后数据集、数据说明文档

- **/paper**：建模论文初稿、修改稿、终稿、参考文献

- **/model**：训练模型、模型参数、模型输出结果

- **/report**：分析报告、图表、可视化结果、答辩材料

- **/docs**：协作说明、日志、修改记录

**文件命名规则**：日期\_姓名\_内容\_版本，例：`20260910_张三_数据预处理_v1.0`

### 3\.2 版本迭代规则

采用**大版本\+小版本**迭代模式，全程保留历史版本，禁止直接覆盖删除：

- **v0\.1\-v0\.9**：初稿、草稿、测试版本（未定稿，持续修改）

- **v1\.0**：首次完整定稿版本

- **v1\.1、v1\.2\.\.\.**：小幅修改、细节优化版本

- **v2\.0**：结构调整、核心内容改动的重大更新版本

所有版本文件全部保留，不得删除旧版本，便于回溯修改过程、核对赛事成果。

## 四、文件修改与协作注意事项（重点）

### 4\.1 修改前注意事项

1\. **必拉取最新内容**：每次修改前必须执行 `git pull`，确保本地文件与远程仓库一致，杜绝版本冲突；

2\. **确认修改权限**：分工明确，每人仅修改自己负责的模块，如需修改他人文件，必须提前沟通告知；

3\. **禁止直接修改主分支文件**：所有修改必须在个人分支完成，审核合并后同步主分支。

### 4\.2 修改中注意事项

1\. **单次修改范围可控**：不要一次性修改大量无关文件，单次提交聚焦一个功能、一个段落、一个问题修复；

2\. **严禁随意删除文件**：旧版本文件、废弃代码、历史数据统一保留，如需清理需团队全员确认；

3\. **禁止上传无关文件**：本地缓存、临时文件、重复文件、个人隐私文件禁止提交到仓库。

### 4\.3 提交推送注意事项

1\. **提交备注必须详细规范**：禁止使用“修改内容”“更新文件”等模糊备注，必须写清「修改人\+修改位置\+修改内容\+修改目的」；

2\. **小步多次提交**：完成一段有效修改就提交推送，不要堆积大量修改一次性提交，便于溯源问题；

3\. **冲突及时沟通解决**：拉取代码出现冲突时，禁止强行覆盖，第一时间联系对应协作成员共同核对修改。

### 4\.4 通用协作禁忌

- 禁止强行推送代码到主分支（git push \-f）；

- 禁止私自修改他人负责的核心文件；

- 禁止提交未测试、存在bug的代码和未校对的论文内容；

- 禁止随意更改仓库目录结构、文件命名规则。

## 五、团队协作约定

1\. 每日比赛工作结束前，全员完成本地修改提交、推送远程，确保仓库同步当日进度；

2\. 重大版本更新（论文定稿、模型最终训练完成等）需在团队内同步公示，全员确认；

3\. 所有修改问题、版本冲突、内容调整，及时在团队群沟通，不私自处理。
